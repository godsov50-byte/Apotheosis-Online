# AO geography database handoff

This directory contains the first database foundation for the S2 geographic registry.

## Current status

- The schema is prepared as a migration; it has **not** been applied to Supabase.
- No new Supabase project was created because the Free organization is at its two-active-project limit.
- Neither existing AO project is used or modified by this migration.
- No S2 seed records are fabricated here. Seed data must come from the registry export generated by the browser's pinned `s2js@1.44.0` implementation.

## Apply later

Apply `migrations/20261120000100_ao_geography_registry.sql` to the dedicated `ao-world-database` project when one is available. The migration creates the private `ao_geo` schema and registry tables.

## Data model

- `registry_versions`: immutable import/version identity and workflow status.
- `cells`: stable S2 cell identity and computed geometry payload. IDs are fixed-width hexadecimal **text**, never SQL numeric values.
- `cell_children`: explicit parent-child hierarchy.
- `cell_neighbors`: same-level edge and vertex-only adjacency.
- `cell_metadata_versions`: versioned names/classification/descriptive metadata, separate from geometry identity.

The S2 geometry payload is JSONB so this initial migration does not assume PostGIS is installed. The source registry retains exact S2 corner vectors and sampled great-circle edges.

## Authority and access boundary

Postgres stores records; it does not decide whether a geographic change is canonical. The AO Kernel must validate and approve an import before it is marked approved. A staged or validated registry version is not automatically canonical.

The schema is not exposed to browser roles. There are no policies for `anon` or `authenticated`, and those roles receive no schema/table grants. Trusted backend ingestion uses `service_role`; never place its key in browser code or commit it to the repository.

## Seed workflow

1. Open the geography globe and export `ao-geographic-registry-v1.json`.
2. Preserve the exported file and compute SHA-256 over the exact bytes.
3. Validate schema version, S2 IDs/tokens, parent-child links, neighbor links, boundary data, and area checks in a trusted ingestion process.
4. Stage the registry version and its records.
5. Have the AO Kernel approve the version; only then mark it `approved`.
6. Keep prior registry versions for auditability; do not silently overwrite S2 identity or geometry.

The browser's local-storage expansion state is a view preference, not canonical world state.
